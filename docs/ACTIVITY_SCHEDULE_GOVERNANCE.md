# Lead Activity Schedule Governance

- The primary planned activity is the lead's current next step, with one active schedule per lead. The current identified assignee may change its date, time, priority or agenda until the earlier of 48 elapsed hours from server-recorded creation and the current due time. Dates and times use UAE time. A move does not change creation time or the original due time. Historical schedules without trusted creation time require Admin review.
- After the limit, the assignee submits a reasoned request. The old schedule stays in force while review is pending. An Admin records a reason for approval or rejection. Approval requires the requester's assignment still to be current, and the proposed due time to be in the future. A resolved activity closes its outstanding request; the request remains in the audit.
- A salesman can log an outcome or cancel after the edit limit. Cancellation is not completion. The system records the claimed occurrence time and server-recorded submission time separately. Corrections append an attributed record with a reason and old/new values; they do not replace the original. Standalone calendar reminders are not promoted to a lead's current next step and do not create rows in the schedule report.
- The Admin Activity view counts distinct scheduled activities, not edit clicks. Due-to-date and on-time rates use the original due time; early cancellations are not counted as due. Completed outcomes, cancellations and distinct rescheduled plans are grouped by the actor who performed or requested the action; overdue open plans are grouped by current assignee. Flagged plans show repeat reschedules and requests to move an overdue activity. This is a review aid, not a ranking.

## Safety and verification

The SQL migration adds schedule metadata and an append-only schedule event table with Admin-only reads. Changes to an existing plan use a protected, version-checked transaction. Direct user writes cannot replace a plan or rewrite the original activity fields and existing audit history. The existing follow-up RPC keeps its public signature; its validated workflow is invoked from a private, actor-checked wrapper so logging an overdue outcome does not require a schedule override.

Run `npm run verify` and `npm run test:ui:management`. `npm run test:activity-schedule-db` exercises the migration in disposable PostgreSQL using the optional local PGlite test dependency.

For the hosted integration rehearsal, use only the isolated ARG Leads CRM Staging project. Set `CRM_RUN_SCHEDULE_STAGING=yes`, set `CRM_DELETION_CHECKOUT` to the separate deletion-approvals candidate checkout, and provide staging-only API credentials and local session and rate-limit secrets in the process environment. Run `node tests/activity-schedule-staging.test.cjs`. The harness uses two local CRM servers, authenticates independent Admin, assigned Salesman and unassigned Salesman sessions, and writes only synthetic records. It signs the test sessions out without deleting the audit evidence.

Approval and restoration of a lead's active reminder must preserve the original plan ID, deadline, and creation timestamp. A previously archived schedule with no saved creation timestamp is restored as a legacy plan requiring review. Successful integration rehearsal is not a production release or verification of a combined deployment.
